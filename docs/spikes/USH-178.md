# USH-178 spike: a live-preview Markdown editor on CodeMirror 6

A spike. Nothing here lands on main. The branch `setmaat/ush-178` shows the
description box as a CodeMirror 6 editor with Obsidian-style live preview, and
this page holds what was measured and what was decided.

## What the branch does

- `src/lib/live-markdown.ts` — our own extension. `pieces()` reads the Lezer
  syntax tree and says what the preview does to each stretch of source;
  `livePreview()` turns that into decorations in one `StateField`. The marks
  hide on every line that no part of the selection touches: headings, bold,
  italic, strikethrough, inline code, fenced code (the fences hide while the
  cursor is outside the block), links (drawn as their words), images from
  `/api/attachments/` (drawn as the image), task items (a tick box that writes
  `[ ]` ↔ `[x]`). Tables stay plain.
- `src/components/board/LiveEditor.tsx` — the CodeMirror box behind the same
  few things a textarea gives `MarkdownBox`: the words, the caret, focus. It is
  loaded with `React.lazy`, so the board page does not carry CodeMirror.
- `MarkdownBox` takes `live`; only the description passes it. The comment
  edit and the composer stay textareas (out of scope).
- `useMentions` now takes a `TextBox` (value, caret, focus, `offsetParent`),
  which a textarea already is and the editor gives. The @ list works inside
  the editor with the same keys: arrows, Enter or Tab picks, Escape closes the
  list only. Drop and paste of a file go through the same upload code.
- Tests: `src/lib/__tests__/live-markdown.test.ts` (what each line draws),
  `e2e/live-preview.spec.ts` (live preview, tick box, @ list, Escape).

## Measurements

All sizes are gzipped, from `next build` of the base commit (af854fe) and of
this branch, summed over the JS files of the board page
(`/p/[projectId]`) and over the new chunks.

| | Board page JS | Editor chunk (lazy) |
|---|---|---|
| Base (textarea) | 252,830 B | — |
| Own extension (this branch) | 253,352 B (+522 B) | 102,885 B |
| Own extension with `@codemirror/lang-markdown` | 253,354 B | 180,444 B |
| `codemirror-live-markdown` 0.5.1-alpha.1 | 253,352 B | 409,950 B |
| … same, without `codeBlockField` | 253,354 B | 408,220 B |

- `@codemirror/lang-markdown` imports the HTML, CSS and JavaScript languages
  and autocomplete: +77 KB for nothing a description uses. The branch builds
  the language from `@lezer/markdown` with `GFM` directly.
- `codemirror-live-markdown` ships one `dist/index.js` of 1.6 MB with every
  highlight.js language inside it and no `sideEffects` flag, so nothing can
  shake it out, even with the code block plugin left out.

### Time to first paint of the panel's editor

Production build on localhost, from the `pointerdown` on the description to two
animation frames after the editor is in the page. Chrome runs with 4× CPU
slow-down.

| | Textarea (base) | Live, first open | Live, open again |
|---|---|---|---|
| Chrome, 390 px phone mode | 25 ms | 336–341 ms | 29–32 ms |
| WebKit, iPhone 13 (390 px) | 31 ms | 330 ms | 31 ms |

The first open pays for parsing the 103 KB chunk and building the editor; on a
phone network the download comes on top. A second open is as fast as the
textarea.

### Phone behaviour (390 px)

Emulated; no real iPhone was available, so autocorrect, the IME, the selection
handles and the scroll under the on-screen keyboard are not proven.

- **WebKit as iPhone 13:** typing writes exactly what was typed, and each line
  turns rendered as the cursor leaves it. A tap on a rendered bold word opens
  that line to its source with the caret in the word. A tap on a tick box
  ticks it in one tap and does not open its line. The @ list opens under the
  box; a tap on a name writes it and keeps focus in the editor.
- **Chrome with a desktop user agent, touch, 390 px:** the same as WebKit,
  except that right after a tap on the bold word the line still read as
  rendered. Check this on a device.
- **Chrome as Pixel 7 (Android user agent):** a synthetic Enter writes no new
  line. CodeMirror's Android path waits for the keyboard's own input event,
  which Playwright does not send. This says nothing yet about a real Android
  keyboard, and must be tried on one.

## Decision: our own extension

1. **Size.** 103 KB against 410 KB for the editor chunk, and the plugin's
   size cannot be cut down from our side.
2. **The plugin does not save us the code.** It has no task-item tick box, and
   `imageField` draws every URL, so a stranger's image would be fetched each
   time the box opens. Both need our own code beside it. What is left is about
   100 lines less than our own, and those 100 lines are the part we must keep
   in agreement with the renderer.
3. **What it brings we do not want:** math (KaTeX), a table editor, a
   copy-button code block, hand-wired mouse listeners, and and hidden marks that
   stay in the DOM as text squeezed to zero width by an animated CSS class
   (`maxWidth: 0`, `opacity: 0`), so the arrow keys walk through characters
   nobody can see.
4. **Risk.** It is 0.5.1-alpha.1 with one maintainer. Ours is 188 lines on
   CodeMirror's stable API, with a test per construct.

## What the editor task (USH-179) must watch for

1. **No `@codemirror/lang-markdown`.** Build the language from
   `@lezer/markdown` with `GFM`, as `live-markdown.ts` does.
2. **Load it lazily, and fetch it early.** The board page stays at +0.5 KB only
   while the editor is a lazy chunk. Start the import when the panel opens,
   so that the ~300 ms first open is gone before the click.
3. **A removed box sends a blur.** React takes the focused editor off the page
   before an effect cleanup runs, and the blur saved a draft that Escape threw
   away. The editor is mounted in a layout effect, whose cleanup runs first.
   Keep it so.
4. **WebKit calls a detached box not editable.** Escape unmounts the box
   before the key reaches the panel's window listener, and the panel then
   closed. `isTyping()` in `keys.ts` now also asks `closest(".cm-editor")`.
5. **Nine end-to-end specs drive the description as a textarea** (`fill`,
   `toHaveValue`): `board`, `card-view`, `editing-sign`, `markdown-wrap`,
   `mention`, `search`, `task-keys`, `text-save`, `upload`. They fail on this
   branch, so the draft PR's CI is red. Give them one helper that types into
   either box.
6. **Agreement with marked.** The unit tests say what each construct draws;
   they do not compare with marked. Add a test that runs one corpus through
   marked's lexer and Lezer and compares headings, emphasis, links, images,
   task items, code and strikethrough.
7. **Android keyboards.** Try Enter, autocorrect and the IME on a real Android
   phone and a real iPhone before the comment box and the composer move over.
8. **Upload on drop and paste** is wired through the editor's own event
   handlers, but no spec proves it yet in the editor.
9. **The comment edit and the composer** keep their textareas until then;
   `MarkdownBox` decides by its `live` prop.
