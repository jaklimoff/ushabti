An agent listens on [the stream](/ushabti/api/events/). A serverless function, a CI job or a chat
bot has nowhere to listen from, so it gives Ushabti a URL and Ushabti posts to it.

A webhook rings the same doorbell the stream rings: **that** something changed and **where**, never
what. No title, no value, no before and after. The receiver reads the board for the rest.

## Make one

**Settings → Webhooks**, at `/p/{projectId}/settings/webhooks`. Only the owner of the project sees
the page, and every route below is `ownerOnly` — the read one included. A URL and a secret are
another road onto the board.

The secret is shown **once**, when the webhook is made. Ushabti keeps it whole, because it signs
every body with it, but nothing shows it again: the page then shows a prefix and **Roll the
secret**.

## The payload

```json
{
  "delivery": "9d2d9d6e-9a6f-4f63-9b1e-6b2b0b6a4c11",
  "projectId": "2f1a7c2e-5f0c-4d4a-9a2e-2b9a3c4d5e6f",
  "projectKey": "USH",
  "kind": "comment",
  "taskId": "7c1b9a2d-3e4f-4a5b-8c9d-0e1f2a3b4c5d",
  "taskKey": "USH-31",
  "at": "2026-03-17T09:46:40.000Z"
}
```

`kind` is one of the words the activity feed writes: `created`, `title`, `description`, `value`,
`checklist`, `comment`, `run`, `archive`, `link`, `deleted`, `reset`. A webhook that names none of
them rings for all of them. A change that writes no feed line — a view, a property, the card view —
rings nothing.

`link` rings both ways, as `deleted` does: a task was made to wait on another, or stopped waiting.
`taskKey` is the task that gained or lost the blocker; the blocker's own key is on the feed line, in
`data.blockerKey`, beside `data.action`, which is `linked` or `unlinked`. A blocker becoming over
rings nothing, because nothing happened to that task.

`taskId` and `taskKey` are **null** on a line about the project rather than about a task. **Send a
test** carries `kind: "test"` and no task, because there is no feed line behind it.

<Aside type="tip" title="`at` is the row, not the send">
`at` is exactly the moment on the activity row, so `GET /api/projects/{id}/activity?after=…` lands
on the line that rang. `delivery` is the same on a retry, so a receiver that remembers the ids it
has seen never acts twice.
</Aside>

## The headers

| Header | What it is |
| --- | --- |
| `X-Ushabti-Delivery` | The delivery id, also in the body |
| `X-Ushabti-Timestamp` | When the body was signed, in seconds |
| `X-Ushabti-Signature` | `sha256=<hex>` over `timestamp + "." + body` |

## Verify it

HMAC-SHA256 with the secret, over the **raw** body, before any JSON parsing. Compare in constant
time and refuse a timestamp older than five minutes.

```js
import { createHmac, timingSafeEqual } from 'node:crypto'

export function verify(secret, headers, rawBody) {
  const time = headers['x-ushabti-timestamp']
  const given = Buffer.from(headers['x-ushabti-signature'] ?? '')
  if (!time || Math.abs(Date.now() / 1000 - Number(time)) > 300) return false
  const want = Buffer.from(
    'sha256=' + createHmac('sha256', secret).update(`${time}.${rawBody}`).digest('hex'),
  )
  return want.length === given.length && timingSafeEqual(want, given)
}
```

A known answer, so you can check your own code before you trust a delivery:

```text
secret     ushs_a-known-secret-for-the-test
timestamp  1774000000
body       {"delivery":"9d2d9d6e-9a6f-4f63-9b1e-6b2b0b6a4c11","projectId":"2f1a7c2e-5f0c-4d4a-9a2e-2b9a3c4d5e6f","projectKey":"USH","kind":"comment","taskId":"7c1b9a2d-3e4f-4a5b-8c9d-0e1f2a3b4c5d","taskKey":"USH-31","at":"2026-03-17T09:46:40.000Z"}
signature  sha256=861a870d23c4a8089c8af6c498dd30e1bafb67b299080feb2ec792de5088f70d
```

## Which addresses are allowed

A webhook is the one request a person tells the server to make for them, so the address has to be
one a stranger could reach too. Ushabti refuses a **loopback** (`127.0.0.0/8`, `0.0.0.0/8`, `::1`,
`localhost`), **private** (`10/8`, `172.16/12`, `192.168/16`, `fc00::/7`) or **link-local**
(`169.254.0.0/16` — the cloud metadata address — and `fe80::/10`) host, and a URL that carries a
name and password. It checks when the URL is saved and again before every try, resolving the name
each time.

<Aside type="caution" title="A private receiver is opt-in">
Set [`USHABTI_WEBHOOK_PRIVATE=1`](/ushabti/start/configuration/#ushabti_webhook_private) on the
server if your receiver really is on that network. Left unset — the default — those addresses are
refused, so a webhook cannot be used to read what else is reachable from the board. The scheme
rule and the no-credentials rule hold whatever the flag says.
</Aside>

## Delivery and retries

The first try goes at once. A failed try is made again after **1 minute**, then **5 minutes**, then
**30 minutes** — four in all. Each one waits **5 seconds** for an answer. Anything outside `2xx`
fails, and so does a redirect.

<Aside type="note" title="A dead endpoint costs one INSERT">
Nothing about a delivery is on the path of a write. A change writes its activity row and one queued
row per webhook, and returns. The sender drains that queue in the background and whenever somebody
reads the board, so a receiver that is down slows nobody's board.
</Aside>

After four failures the delivery is dropped. Catching up is the feed's job, which is the record:
`GET /api/projects/{projectId}/activity?after=…`.

The last **20** deliveries of each webhook are kept; the page reads the newest of them for its
_delivered 2m ago_ line.

## The routes

| What | Call |
| --- | --- |
| The list, with each one's last delivery | `GET /api/projects/{projectId}/webhooks` |
| Make one, and read its secret once | `POST /api/projects/{projectId}/webhooks` |
| URL, kinds, on or off, or `{"roll": true}` | `PATCH /api/projects/{projectId}/webhooks/{id}` |
| Send a test | `POST /api/projects/{projectId}/webhooks/{id}` |
| Delete it | `DELETE /api/projects/{projectId}/webhooks/{id}` |

## What a receiver should do

1. Check the signature. Refuse what fails, with `401`.
2. Answer **fast** — `200` and nothing else — then do the work. Five seconds is all the sender
   waits.
3. Remember the delivery ids you have seen and skip a repeat.
4. Read `/activity?after=…` for what actually happened, from a few seconds before your cursor, and
   skip the entries you have handled: two writes can commit out of the order of their clocks.
