Every route on this page accepts an agent token, except one: the column sweep,
`POST /api/projects/{projectId}/archive`, is a person's. Content is shared; clearing a whole column
is a decision about the board.

---

## `POST /api/projects/{projectId}/tasks`

Creates a task, gives it the next number in the project and a rank, and optionally writes its first
values.

```json title="request"
{
  "title": "Write the offline queue tests",
  "description": "Cover the retry path.",
  "values": { "<statusPropertyId>": "<optionId>" },
  "atTop": true
}
```

| Field | Rules |
| --- | --- |
| `title` | required, ≤ 400 characters |
| `description` | optional, ≤ 20000 characters |
| `values` | optional, `{ propertyId: value }` — see [value shapes](/ushabti/api/properties/#value-shapes-by-type) |
| `afterId` | optional — place it straight after this task |
| `atTop` | optional — only read when `afterId` is absent |

Neither placement field means the end of the board.

```json title="201"
{ "task": { "id": "…", "number": 14, "key": "USH-14", "title": "…", "description": "",
            "position": "Vk", "projectId": "…", "createdBy": "…", "createdAt": "…", "updatedAt": "…",
            "archivedAt": null } }
```

<Aside type="caution" title="A bad value in `values` still leaves you a task">
The row is committed before the values are written, so a rejected value answers `400` on a task that
now exists with the rest of the values applied. Read the task back if the answer was not `201`.
</Aside>

## `GET /api/tasks/{taskId}`

The task in full — everything the panel shows.

```jsonc title="200"
{
  "task": {
    "id": "…", "number": 14, "key": "USH-14",
    "title": "…", "description": "…",
    "position": "Vk", "createdAt": "…", "updatedAt": "…",
    "archivedAt": null,                 // the moment it was archived, or null
    "values": { "<propertyId>": "<value>" },
    "checklistTotal": 4, "checklistDone": 2, "commentCount": 3,

    "checklist": [
      { "id": "…", "text": "Cover the retry path", "done": true, "position": "V" }
    ],

    "comments": [                       // oldest first
      { "id": "…", "body": "tests are green",  "createdAt": "…",
        "author": { "id": "…", "name": "Builder", "color": "#3fb0c8" } }
    ],

    "activity": [                       // NEWEST first, at most 60
      { "id": "…", "kind": "value", "createdAt": "…",
        "data": { "property": "Status", "value": "In Progress" },
        "actor": { "id": "…", "name": "Ada", "color": "#6d5bd0" } }
    ],

    "run": null,                        // or the open run, with `steps` and the last 40 `log` lines

    "pastRuns": [                       // the runs that are over, NEWEST START first, at most 20
      { "id": "…", "goal": "Write the queue tests", "step": "…", "status": "done",
        "startedAt": "…", "endedAt": "…",
        "agent": { "id": "…", "name": "Builder", "color": "#3fb0c8" } }
    ]
  }
}
```

A row of `pastRuns` is a run without its plan and its log, and without the three fields those would
have to be read for: `stepsTotal`, `stepsDone` and `lastLog` are on an open run and **not** on a
history row. It says who ran this, when, and how it ended. Ask
[`GET /api/runs/{runId}`](/ushabti/api/runs/#get-apirunsrunid) for one of those in full; it answers
for a closed run exactly as it does for an open one, counts and plan and log and all.

`activity.kind` is one of `created`, `title`, `description`, `value`, `checklist`, `comment`, `run`,
`archive`, `deleted`. An `archive` entry carries `data.action`, which is `archived` or `restored`.
`author` and `actor` are `null` when the user row has been deleted.

This route answers for an archived task exactly as it does for a live one, which is what makes a
link to one still open it.

<Aside type="note" title="A 200 with a null task is possible">
If the row disappears between the lookup and the read, the answer is `{"task": null}` at `200`.
</Aside>

## `PATCH /api/tasks/{taskId}`

```json title="request"
{ "title": "…", "description": "…" }
```

Both optional, ≤ 400 and ≤ 20000 characters. `""` clears the description. `200 {"ok": true}`.

## `DELETE /api/tasks/{taskId}`

Deletes the task with its values, checklist, comments and runs. `200 {"ok": true}`.

<Aside type="caution" title="An agent can delete a task">
This route carries no gate. If that is not what you want from an agent, say so in its instructions —
the bundled skill does. Archiving is the everyday way to make a task go away; delete is for a
mistake.
</Aside>

## `POST /api/tasks/{taskId}/archive`

Archives the task. It leaves every board and every list, and keeps its values, its checklist, its
comments, its history and its link. The body is empty. `200 {"ok": true}`.

## `DELETE /api/tasks/{taskId}/archive`

Puts an archived task back. It returns to the rank it never lost. `200 {"ok": true}`.

Both are member calls, an agent's as much as a person's: an agent may archive the task it finished,
as it may close its own run. Both write an `archive` entry to the activity log and ring the stream.

**Both are idempotent.** Each says what the task should be, so a call that changes nothing answers
`200 {"ok": true}`, writes no activity line and rings nothing: archiving an archived task keeps the
moment it first went, and putting a live task back is a no-op. Retry either as often as you like.

## `POST /api/projects/{projectId}/archive` <Badge text="person only" variant="caution" />

Archives every live task in one column: the sweep behind **Archive everything in this column**.

```json title="request"
{ "propertyId": "<statusPropertyId>", "value": "<optionId>" }
```

The body names a property and a value rather than a column, because a column is one value of the
property the view groups by and the server has no idea what a column is. `"value": null` is the
column of the tasks that hold nothing there.

```json title="200"
{ "archived": 42 }
```

The answer is how many tasks went. One call can clear a whole column, so this one is a person's:
an agent gets `403`.

## `POST /api/tasks/{taskId}/move`

One drag in one call: a new rank, and optionally the column value the card landed on.

```json title="request"
{ "beforeId": "<taskId>", "values": { "<statusPropertyId>": "<optionId>" } }
```

| Field | Means |
| --- | --- |
| `beforeId` | land **in front of** this task. Wins over `afterId`. |
| `afterId` | land **after** this task. Only read when `beforeId` is absent. |
| `values` | the column change, written in the same call |
| *neither id* | the end of the board |

```json title="200"
{ "position": "Vkm" }
```

The answer is the authoritative new rank.

<Aside type="tip" title="The neighbour is the global neighbour">
Ranks are computed against the project's whole task list, not against the target column — so
`beforeId` must name the task that really is the neighbour in the board's one order, which for a
grouped or filtered board is the card the user can see next to it.
</Aside>

Concurrent moves are serialised behind a per-project lock, so two people dragging at once cannot
compute the same rank.

## `PUT /api/tasks/{taskId}/values/{propertyId}`

Writes one value. **This is the main agent write.**

```json title="request"
{ "value": "<optionId>" }
```

```json title="200"
{ "value": "<optionId>" }
```

Read the answer rather than assuming: values are normalised on the way in — a multi-select is
deduplicated, `"42"` becomes the number `42`, and text is truncated at 2000 characters.

**To clear a value**, send `null`, `""`, or omit the key entirely. That stores `null`, or `[]` for a
multi-select.

The accepted shape depends on the property's type —
see [value shapes](/ushabti/api/properties/#value-shapes-by-type).

| Status | Message |
| --- | --- |
| `400` | `That property is not in this project.` |
| `400` | `Priority needs one option.` · `One of the options does not exist any more.` · `Due needs a date like 2026-08-21.` |

## `POST /api/projects/{projectId}/tasks/values`

Writes **one property on many tasks**, in one call. It is what the board's **Set…** does with the
cards you picked.

```json title="request"
{
  "taskIds": ["…", "…", "…"],
  "propertyId": "<priorityPropertyId>",
  "value": "<optionId>"
}
```

```json title="200"
{ "set": 3, "value": "<optionId>" }
```

`value` takes exactly the shapes the single-value route takes, and is checked **once** for all of
them — so the value that reaches one task is the value that reaches every task. One line of
activity is written for each task, the same `value` line the single route writes, and the board
rings once.

It takes an agent token. A value is content, and an agent may already write ten of them with ten
calls; this is the same work in one call. There is **no project lock**, because the lock serialises
the writes that compute a rank and this touches none.

| Field | Rules |
| --- | --- |
| `taskIds` | required, a list of ids, **200 at most**. The same id twice counts once. |
| `propertyId` | required, a property of this project |
| `value` | as for one task — `null` or `""` clears it |

| Status | Message |
| --- | --- |
| `400` | `Name the tasks as a list of ids.` · `Name at least one task.` · `That is more than 200 tasks. Set fewer at once.` |
| `400` | `Name the property to set.` · `That property is not in this project.` |
| `400` | `One of those tasks is not on this board.` |
| `400` | `One of those tasks is archived. Put it back first.` |

<Aside type="note" title="All of it, or none of it">
One bad id refuses the whole call. Writing what it could reach would leave the board half set, and
the answer would then have to say which half — which is the thing one call exists to avoid. An
archived task is refused with the rest: no view draws one, so it cannot be picked on a board, and
setting a property on a card nobody can see is a change with nothing to show for it. Put it back
first, which is one press on the archive page.
</Aside>

## Checklist

### `POST /api/tasks/{taskId}/checklist`

```json title="request"
{ "text": "Cover the retry path" }
```

`text` required, ≤ 400 characters. `201 { "item": { "id", "taskId", "text", "done", "position" } }`.

### `PATCH /api/checklist/{itemId}`

```json title="request"
{ "text": "…", "done": true }
```

Both optional. `done` is coerced, so any truthy JSON works.

```json title="200"
{ "item": { "id": "…", "taskId": "…", "text": "…", "done": true, "position": "V" } }
```

Send neither field and the answer is `{"ok": true}` instead — a different shape, and no write.

### `DELETE /api/checklist/{itemId}`

`200 {"ok": true}`. There is no reordering for checklist items.

## Comments

### `POST /api/tasks/{taskId}/comments`

```json title="request"
{ "body": "tests are green" }
```

The field is literally `body`. Required, ≤ 8000 characters. An agent comments as itself.

```json title="201"
{ "comment": { "id": "…", "taskId": "…", "authorId": "…", "body": "…", "createdAt": "…",
               "author": { "id": "…", "name": "Builder", "color": "#3fb0c8" } } }
```

### `DELETE /api/comments/{commentId}`

Your own comment, or anybody's if you are the owner. `403 You can only delete your own comments.`
otherwise.

An agent may delete its own comments — this is the one owner check written without the human gate.

<Aside type="note" title="Comments cannot be edited">
There is no `PATCH`. A comment is a thing somebody said.
</Aside>
