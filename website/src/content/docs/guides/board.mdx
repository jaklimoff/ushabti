The board is the product. Everything else — settings, the panel, the API — exists to keep it honest.

<Image src={board} alt="An Ushabti board with four columns, coloured tags on the cards, and an agent working on one of them." class="shot" />

## Moving a card

Drag it. Cards move inside a column and between columns; dropping one on the free space below a
column's cards sends it to the end of that column. A drag has to travel five pixels before it counts,
so a click still opens the card.

Moving a card to another column **writes the grouping property's value for that column**. Dragging
a card from Todo to In Progress is not a special board operation; it sets `Status = In Progress`.
That is the same write the panel makes, and the same one an agent makes over the API.

<Aside type="note" title="Nothing here is picked by the distance between corners">
A column is as tall as the board, so an empty one has two corners hundreds of pixels away and would
lose every distance contest to a small card one column further over. Ushabti asks *what is under the
pointer* first, and *which rectangles overlap* second. Corner distance only settles the gaps.
</Aside>

## Moving a column

Each column header carries a six-dot grip. Drag it and you **reorder the options of the grouping
property** — for everybody, and in every view that groups by it. Three conditions:

- Only when the grouping property is a **select**. Person and checkbox columns have no order to
  change.
- The `No status` column never moves; it is always last.
- **Not while a filter names the grouping property.** A drop can only say which column it landed
  after, and through a partial view you would be ranking an option after a column somebody else
  cannot see.

## Folding a column

Each column header carries a **«** beside its **+**. Press it and the column folds to a narrow
strip that still shows its name and how many cards are in it. Press the strip and it opens again.

A fold is **yours alone**. It is kept in your browser, per view and per column, so it survives a
reload and reaches nobody else's board. Nothing about it is written to the project, and an agent
reading the API sees a board that never folded.

A folded column is **still a drop target**: drag a card onto the strip and it lands at the end of
that column, exactly as dropping it on the free space below the cards would. Nothing can be lost on
a strip.

The arrow keys step over a folded column the way they step over an empty one, because it draws no
cards to land on — see [Keyboard](/ushabti/guides/keyboard/). A folded column cannot be dragged to a
new place; open it first. Its order belongs to the option everybody shares, while the fold belongs
to your browser.

<Aside type="tip" title="Folding is not archiving">
Folding gives the width back and hides nothing from anybody else: a column you fold is still on the
board, still counted, and still takes cards. To empty a column for everybody, archive it.
</Aside>

## Archiving a column

Each column header carries **↓** beside its **+**. It asks in the header itself, in real numbers:

> Archive 42 tasks in Shipped? They leave the board and keep their history.

**Yes, archive** takes every card in that column off every board and every list, and a toast says
how many went — the server's count, not the one the question named a moment earlier. Nothing is
deleted: each task keeps its values, its checklist, its comments, its history and its link, and any
one of them can be put back from its own panel — see
[the task panel](/ushabti/guides/task-panel/#archived-and-put-back).

This is the answer to a Shipped column that grows without limit. What went is on
[the archive page](#the-archive).

- **A person only.** One press can clear forty cards, so an agent cannot make this call. An agent
  may archive the one task it finished.
- **Not while a filter is on.** The button is absent then. The sweep names a value of the grouping
  property, so under a rule it would archive tasks this board is not drawing — and the count in the
  question would not be the count that went. Clear the filter and the button is back.

## The archive

**Archive** in the top bar, beside **Settings**, opens `/p/{project}/archived`: every archived task
of the project, newest first, with the key, the title and when it went. It is not a view — no view
draws an archived task — which is why it is a page of its own and not a pill in the view strip.

- **The key and the title open the task**, exactly as its link does.
- **Put back** returns one to the rank it never lost, so it lands where it was. The row goes, and a
  line says which task is back.
- **The box at the top narrows the list** by key and title, which are what a row shows.

The page draws the archived tasks your browser already carries, so it answers as you type and asks
the server nothing until you put one back. Who archived a task is not on the row: open it and the
[activity log](/ushabti/guides/task-panel/#activity) says who and when.

## Deleted, gone in 30 days

Below the archived list, the same page holds the other kind of gone: **Deleted, gone in 30 days**,
drawn only when there is something in it.

A deleted task is off every board and every list, out of every search and every count. It is not
half gone: its link opens nothing, and anything that asks the API about it is told there is no such
task. For thirty days it is still here, and **Put back** on its row returns it whole — with the key
it had, the rank it had, and its values, its checklist, its comments and its history. A task you
deleted while it was archived comes back archived.

**The delete itself says so**, in one line at the bottom of the board: _USH-14 deleted. Put it back
from the Archive within 30 days._ There is no button on it — a way back that lives in something
that goes in five seconds is not a way back — so it names the page instead, which is in the top bar
beside **Settings**.

- **Newest first**, with when it went and how many days are left.
- **The key and the title open nothing**, unlike an archived row. There is nothing to open until it
  is back.
- **Put back asks nothing first.** It takes nothing away, so there is no cost to name.

After the thirty days the task is taken away for good, and everything on it goes too. The window is
the same for every project and it is not a setting.

<Aside type="note" title="What a delete undoes, and what it does not">
This is undo for a deleted task, and for nothing else. A property you delete, an option, a view or
a value you overwrite has no way back — the row that asks names what goes with it, in real numbers,
before anything happens.
</Aside>

## Adding a column

**+ New column** at the right end, shown only when the grouping property is a select. Type a name,
press Enter. It adds an option to the grouping property, so the column appears on everybody's board.

If the current view has an `is` rule on the grouping property, **the new option joins that rule** —
because nobody makes a column in order not to see it.

## Ordering the cards

The cards in a column are in `position` order, top to bottom — the one order every view in the
project shares — until you ask for another one.

**Press Sort in the view strip.** A board has no headings to press, so the order is asked for beside
**Filter**. The panel lists everything a card carries: press a row for smallest first, press it
again for largest first, and a third time for the order the board itself keeps. **Every column** is
drawn in that order, and a chip above the board names it so you can see at a glance that the board
is not in its own order. The `✕` on the chip is the other way back.

It is the same order a list gets from its headings, decided by the same rules — which column kinds
order which way, and why a task that holds nothing goes last, are in
[The list](/ushabti/guides/list/#ordering-by-a-column). The order is remembered on the view, so
everybody looking at that view sees it, the way they see its filters.

A sort **writes nothing**. The rank each task carries is untouched. A task you add while an order
is on lands where the order puts it, not at the top or the end you pressed.

<Aside type="caution" title="A sorted column cannot be rearranged">
A drag writes a rank, and a sorted board is not showing ranks — dropping a card between two others
would write an order nobody on the screen can see and then leave the card where the sort puts it.
So while an order is on, the cards inside a column hold still and <kbd>↑</kbd> <kbd>↓</kbd> do not
move a lifted one.

**Dragging a card to another column still works**, because that writes the column's value and no
rank at all; the card lands where the order puts it. So does dragging a column header, which writes
the option order. Only the place a card has inside its column is the sort's to give.
</Aside>

## Adding a task

Two places, and they mean different things:

- The **+** in a column header — adds to the **top** of that column.
- The empty area below the cards — adds to the end. It reads **Add a task** when the column is
  empty.

Both open a composer with the placeholder *"What needs doing?"*. **Enter** adds it (Shift+Enter is a
newline), **Escape** cancels, and clicking away with text in the box also adds it. The new task's
panel opens straight away.

Under the box is a line saying what will happen: `Enter to add · Esc to cancel`, or
`Enter to add · sets Priority Urgent` when a filter is going to fill something in. The composer says
what it will write before it writes it — see [Filters](/ushabti/guides/filters/).

## Blocked by

A task can say which tasks it waits on. Open the task, press **⋯** and choose **Blocked by…**, then
type the key or the title of the task that blocks it. **Blocks** is the other end of the same
chain, and each list adds the same way, by the **+** beside its heading.

A row is a key, a title and a **✕**. The ✕ asks nothing: unlinking costs one key to undo, and the
question is for what cannot be undone.

The card says one thing about it: a small grey chain beside the key, with the blockers in its
tooltip. Never a list and never a count — a board where half the cards are waiting has to stay
readable, and the panel is where the chain lives. It is drawn rather than typed, so it is the same
shade and the same shape whatever fonts a machine has.

**A blocker stops blocking when it is over.** Over means archived, and it also means the one option
the owner named under **Done when** in [Settings → Project](/ushabti/guides/settings/#the-project-page).
Archive the blocker and the chain glyph goes by itself; the link is still there, struck through in
the panel, because it happened.

A circle is refused with one sentence — *USH-12 already waits on USH-71, so this would be a circle.*
— and so is a task told to wait on itself. Nothing is written when either is refused.

A task with no links draws nothing at all in the panel. That is why the way in is the menu: a
heading over an empty list, on every task in the project, would cost more than the line it saved.

<Aside type="note" title="One link kind, on one board">
`blocks` is the only kind of link there is, and both ends have to be tasks on the same board. There
is no graph, no Gantt and no dates — see [the roadmap](https://github.com/jaklimoff/ushabti/blob/main/ROADMAP.md).
</Aside>

## Picking several cards

Moving ten cards to a new owner one at a time is the tenth-time friction a team notices most. So a
card can be **picked**, and one answer goes on all of them.

There is no mode to turn on. Hover a card and a check appears in its top-left corner; press it and
the card is picked. Once anything is picked, every card shows its check, so the way out is where the
way in was.

<div class="keys">

| How | What it picks |
| --- | ------------- |
| The check in the corner | That card, or puts it back. |
| <kbd>Shift</kbd> + click a card | Every card from the last one you picked to this one, **inside one column**. In another column it picks that one card and starts again from it. |
| <kbd>x</kbd> | The card the cursor is on, or puts it back. It is the whole keyboard route in, because the board keeps [one tab stop](/ushabti/guides/keyboard/). |

</div>

A plain click still opens the task, and <kbd>Space</kbd> still lifts a card for a drag. A picked card
**wears a border and nothing more**: a board with ten picked cards on it has to stay readable.

While anything is picked, a small bar stands in the top bar beside the search box:

> **3 selected** · Set… · Archive · ✕

**Set…** asks the same two questions the filter asks, in the same panel: which property, then what
about it. The answer goes on every picked card in one write, so the board never ends up half set. The
picks stand afterwards, because setting a second property on the same cards is the next thing anybody
does.

**Archive** takes the cards off the board. It asks first, and the bar itself is the question —
*Archive 3 tasks?* — because the board has no dialogs. The cards keep everything they had and are on
the [archive page](#the-archive), one press from coming back. Unlike **Set…**, it ends the
pick: the cards are gone, so there is nothing left to count.

**✕** or <kbd>Escape</kbd> ends it, and so does moving to another view. With the question standing,
<kbd>Escape</kbd> takes the question away first and leaves the picks.

<Aside type="note" title="A filter hides a card; it does not unpick it">
The bar counts what this view is drawing. Pick three cards, add a rule that hides one of them, and
the bar reads *2 selected* — and **Set…** writes two. The third is not lost; it is hidden, exactly as
it is on the board behind. Nothing you cannot see is quietly written to.
</Aside>

On a phone the bar takes the room it needs: the project name goes, and below 560 px so do the search
box and the two links off the board. The question is longer than the count, so while it stands the
project mark goes too. Everything comes back the moment nothing is picked.

A [list](/ushabti/guides/list/) picks the same way, with the same bar.

## On a phone

Below **560 px** the board draws **one column, the width of the screen**, and stops scrolling
sideways. Two 272 px columns need 576 px, so below that a second one cannot honestly be drawn.
Above 560 px nothing changes at all.

Over the column is a **strip of column pills**: a dot, the name, and how many cards are in it, with
the column on screen filled. It sits below the filter chips and above the board, and it is not a
second view strip — it names columns rather than views, it carries no sort and no filter, and its
pills never drag, because the column order belongs to the property everybody shares. **+ New
column** is the last pill.

Three ways reach another column, and all three move the same one thing:

<div class="keys">

| How | What it does |
| --- | ------------ |
| A pill | Shows that column. |
| A swipe | 60 px sideways, and further sideways than up or down. A finger going left brings in the next column; going right, the one before. A finger going up or down scrolls the column, as it always did. |
| <kbd>←</kbd> <kbd>→</kbd> | The same keys the board has everywhere else. The cursor walks to a card in the next column that has one, and the board follows it there — see [Keyboard](/ushabti/guides/keyboard/). |

</div>

A board **opens on the first column every time**. Which column you were on is not remembered: it
would be a second hidden state, and the strip above says where you are in one glance.

What is different down here, and why:

- **No drag.** There is one column on screen, so a card has nowhere to be carried. To move a card,
  open it and set the grouping property in the panel — that is the one value a drop across a board
  writes. **Set…** in the [pick bar](#picking-several-cards) does several at once. With the drag
  sensors off, a finger going sideways belongs to the board.
- **No column drag**, for the same reason, and **no folding**: a fold gives width back, and there is
  no width here to give. A fold you made on a wider window is ignored rather than cleared, so the
  wider window gets it back.
- **The check that picks a card is always drawn**, on a card and on a list row, because a finger
  cannot hover.

A [list](/ushabti/guides/list/) changes nothing on a phone: it is one column of rows already, so it
has no strip, and a row keeps its columns.

## When the board is empty

Two different empty states, because they mean two different things.

**No task passes the filter** — with a **Clear the filter** button. Your work is there; you asked a
question it does not answer.

**Nothing at all yet** — and the board takes the chance to explain itself:

> The columns come from a property called **Status**. So do Priority, Assignee and the rest — every
> field on a task is yours to rename or delete in Settings.

## Live updates

Somebody else moves a card, edits a title, adds a column, renames a property or changes a filter,
and your board follows in about a second with no reload.

The mechanics, in case a number matters to you: one `EventSource` per tab, fed by Postgres
`LISTEN`/`NOTIFY`, so any Ushabti process on the same database sees every write. Incoming events are
debounced by 140 ms and then the board is refetched. **The event says what changed, never how** —
there is no payload to get out of order. Your own writes are tagged and skipped, so your tab never
refetches because of you.

The board also re-syncs whenever the stream connects — first open, and after every reconnect. Events
have no replay, so anything broadcast while you were reconnecting would otherwise be lost for good.

<Aside type="tip" title="Every open board holds one database connection">
For live updates, outside the pool. It matters when you point Ushabti at a small managed cluster —
see [Configuration](/ushabti/start/configuration/).
</Aside>
